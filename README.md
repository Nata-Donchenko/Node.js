# ДЗ 32. REST API для інтернет-магазину

REST API спрощеного інтернет-магазину з двома базами даних:

- **MySQL** — основні сутності: користувачі, товари, атрибути товарів, налаштування користувачів;
- **MongoDB** — аналітика: кожен виклик API зберігається як окрема подія.

## Технології

- Node.js (чистий JavaScript, ES-модулі)
- Express 5
- Sequelize + mysql2 — робота з MySQL
- Офіційний драйвер `mongodb` — аналітика
- bcrypt — хешування паролів
- jsonwebtoken — автентифікація через JWT
- dotenv — змінні оточення

## Запуск

1. Встановити залежності:
   ```bash
   npm install
   ```
2. Створити файл `.env` на основі `.env.example` і заповнити:
   ```
   PORT=3000
   MYSQL_URL=mysql://root:your_password@localhost:3306/shop_db
   MONGODB_URL=mongodb://localhost:27017/shop_analytics
   JWT_SECRET=your_jwt_secret
   JWT_EXPIRES_IN=1h
   BCRYPT_SALT_ROUNDS=10
   ```
3. Розгорнути базу MySQL одним із двох способів:
   - **з дампу** (база створиться разом із тестовими даними):
     ```bash
     mysql -u root -p < dumps/shop_db.sql
     ```
   - **з нуля**: виконати `CREATE DATABASE shop_db;`. Таблиці створить Sequelize під час запуску сервера.
4. (Необов'язково) Імпортувати аналітику в MongoDB:
   ```bash
   mongoimport --db shop_analytics --collection analytics_events --file dumps/analytics_events.json --jsonArray
   ```
   База MongoDB створюється автоматично з першою подією, тож без імпорту теж усе працює.
5. Запустити сервер:
   ```bash
   npm run dev
   ```

## Ендпоінти

| Метод | Адреса | Автентифікація | Опис |
|---|---|---|---|
| POST | `/users/register` | — | Реєстрація. Тіло: `email`, `password`, `isOwner` (необов'язково) |
| POST | `/users/login` | — | Вхід, повертає JWT |
| GET | `/users/:id` | — | Профіль користувача (без хешу пароля) |
| POST | `/products` | JWT + роль власника | Створення товару |
| GET | `/products` | — | Список товарів |
| GET | `/products/:id` | — | Деталі товару |
| PUT | `/products/:id` | JWT + власник цього товару | Редагування товару |
| DELETE | `/products/:id` | JWT + власник цього товару | Видалення товару |
| POST | `/products/:id/attributes` | JWT + власник цього товару | Додати атрибут. Тіло: `name`, `value` |
| GET | `/products/:id/attributes` | — | Усі атрибути товару |

Токен передається в заголовку:
```
Authorization: Bearer <token>
```

### Коди відповідей

| Код | Коли |
|---|---|
| 400 | Не передані обов'язкові поля |
| 401 | Немає токена, токен недійсний або прострочений, невдалий логін |
| 403 | Користувач не є власником (створення товару) або товар належить іншому користувачу |
| 404 | Користувача або товар не знайдено |
| 409 | Email уже зареєстрований |

## Обґрунтування рішень

### Власник товару (Вимога 2)

Обрано підхід із **прапорцем `is_owner`** у таблиці `users`. Товари можуть створювати лише користувачі з `is_owner = true`, а кожен товар через `owner_id` (зовнішній ключ на `users.id`) посилається на конкретного власника.

Так розділяються ролі: звичайний покупець не може виставляти товари на продаж. Прапорець задається під час реєстрації (`"isOwner": true`). Це спрощення для навчального проєкту: у реальному магазині роль продавця видавав би адміністратор або вона б підтверджувалась окремо.

Перевірки:
- `POST /products`: без валідного токена — 401, якщо `is_owner = false` — 403;
- `PUT` і `DELETE /products/:id`: якщо товар належить іншому користувачу — 403.

`ownerId` нового товару береться **з токена**, а не з тіла запиту, щоб користувач не міг створити товар від чужого імені. Під час редагування оновлюються лише дозволені поля (`name`, `description`, `price`), тож змінити власника через тіло запиту неможливо.

Перевірку власника винесено в окремий middleware `productOwnerMiddleware`. Він знаходить товар, перевіряє власника і передає товар контролеру через `req.product`. Так перевірка не дублюється в трьох контролерах (редагування, видалення, додавання атрибутів). Логіка лишається тією ж, що вимагає завдання, просто записана в одному місці.

### Атрибути товарів (Вимога 4)

Атрибути зберігаються за моделлю **EAV** (Entity–Attribute–Value) в одній таблиці `product_attributes`: кожен атрибут — окремий рядок `product_id — attribute_name — attribute_value`.

Так у футболки можуть бути колір, розмір і матеріал, а в ноутбука процесор, пам'ять і екран, без додавання колонок у `products` і без порожніх клітинок. Новий тип товару не потребує змін структури бази. Під час видалення товару його атрибути видаляються автоматично (`ON DELETE CASCADE`).

### Налаштування користувача (Вимога 5)

Обрано **комбінований підхід**: фіксовані колонки + колонка типу `JSON` у таблиці `users`.

| Налаштування | Де зберігається | Чому |
|---|---|---|
| Мова (`language`) | окрема колонка, за замовчуванням `uk` | просте значення, є в кожного, за ним можна шукати й фільтрувати |
| Валюта (`currency`) | окрема колонка, за замовчуванням `UAH` | те саме |
| Тема, сповіщення та інше | колонка `settings` типу `JSON` | довільна структура з вкладеністю, набір полів може відрізнятися |

Альтернативи:
- **лише `JSON`** — найгнучкіше, але за найпоширенішими налаштуваннями незручно шукати;
- **окрема таблиця «ключ — значення»** (як атрибути) — губить вкладеність і типи: `{ "notifications": { "email": true } }` довелося б розплющувати на кілька рядків з рядковими значеннями `"true"`.

Налаштування зберігаються прямо в `users`, бо зв'язок один-до-одного: так налаштування видно разом із профілем, без додаткових запитів до інших таблиць.

### Аналітика в MongoDB (Вимога 6)

Аналітичні події — це потік записів, який швидко росте, не має зв'язків з іншими таблицями і має різну структуру для різних ендпоінтів. Тому вони зберігаються окремо в MongoDB, в колекції `analytics_events`.

**Як працює:** глобальний middleware `analyticsMiddleware` підписується на подію `finish` об'єкта відповіді і викликає `next()`. Подія записується в MongoDB **після** того, як клієнт отримав відповідь, тож запис не затримує API. Помилки запису ловляться й виводяться в консоль, не впливаючи на роботу сервера.

**Структура документа:**
- спільні поля для всіх подій: `type`, `method`, `endpoint`, `timestamp`, `statusCode`, `durationMs`;
- поле `details` — **унікальне для кожного ендпоінта**. Контролер кладе туди свої дані через `res.locals.analytics`.

Тип події визначається за шаблоном маршруту (`req.baseUrl + req.route.path`), тому подія отримує правильний тип навіть тоді, коли запит зупинився на етапі автентифікації (401) і контролер не виконувався. Запити на неіснуючі адреси записуються як `unknown_request`.

Приклади `details` для різних подій:

```json
// user_login (невдала спроба)
{
  "email": "owner1@shop.com",
  "success": false,
  "failureReason": "wrong_password",
  "client": { "ip": "::1", "userAgent": "PostmanRuntime/7.x" }
}

// product_create
{
  "productId": 6,
  "ownerId": 3,
  "product": { "name": "Термочашка", "price": 399.99 }
}

// product_update
{
  "productId": 2,
  "ownerId": 1,
  "changedFields": ["price"]
}

// attribute_list_view
{
  "productId": 5,
  "count": 3
}
```

Такі документи з різними полями, вкладеними об'єктами й масивами незручно розкласти на одну SQL-таблицю з фіксованими колонками. Довелося б або створювати десятки колонок, більшість з яких порожні, або окрему таблицю під кожен тип події. Документоорієнтована база зберігає їх як є.

Клієнту під час невдалого логіну повертається однакове повідомлення (`Invalid email or password`), щоб не розкривати, чи існує email. А в аналітику записується справжня причина (`user_not_found` / `wrong_password`), бо її бачать лише розробники.

## Дампи

- `dumps/shop_db.sql` — дамп MySQL (структура + дані): 5 користувачів (3 власники, 2 покупці), 6 товарів від трьох різних власників, 8 атрибутів, налаштування з різною структурою;
- `dumps/analytics_events.json` — експорт колекції `analytics_events` з MongoDB: 47 подій різних типів (реєстрації, успішні й невдалі логіни, створення, перегляди, редагування й видалення товарів, атрибути, відповіді 401/403/404, невідомі запити).

Тестові користувачі мають пароль `12345`.
